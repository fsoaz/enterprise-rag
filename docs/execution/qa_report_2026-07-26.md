## 1. Executive Summary

### Overall quality

This is an unusually well-planned system with a partially-built product underneath it. The documentation set (`product.md`, `architecture.md`, `roadmap.md`, `api_rules.md`, `testing.md`) is of a standard rarely seen in an MVP — explicit ADRs, benchmark profiles that refuse to publish a latency number without a workload behind it, a review register that names its own past mistakes. The engineering that *is* present is careful: RLS is enabled **and forced** on all 21 tenant tables, ACLs compile into the ranking query rather than post-filtering, tenant context is transaction-local and re-applied on `after_begin`, the identity lookup refuses to guess between two tenants sharing an `external_subject`.

The gap is between that plan and what a user can actually do. The chat UI is 377 lines and holds exactly one question and one answer. The admin UI is an upload form. Two of the six advertised differentiators — freshness/versioning and the evaluation dashboard — have no reachable code path in the product. And the two mechanisms the product is *named for* (grounded answers, refusal to guess) do not work in the configuration the repository ships.

### Main strengths

- **Tenant isolation is real and verifiable.** `globex-member` searching for `acme` content returns `{"data":[],...}`. RLS forced on every tenant table, with a BYPASSRLS identity path kept narrow and deliberate.
- **ACL pre-filtering works on documents and search.** `acme-viewer` and `acme-member` receive demonstrably different document lists and different search hits from the same query.
- **Input validation is genuinely good.** Empty/null/oversized questions → 422 with field-level RFC 7807 errors. `top_k=9999` → 422. Unknown strategy → 422 enumerating the legal values. SQL injection strings are parameterized through and cause no damage. Real binaries (`.ico`, ZIP) → 415 by content sniffing, not by trusting `Content-Type`.
- **Authorization is enforced consistently on writes.** Upload/archive as `member` or `viewer` → 403. Erase as `steward` → 403. Feedback on another user's query → 404 (correctly, not 403). Uploading into another tenant's collection → 404.
- **Rate limiting and lifecycle semantics hold.** Chat capped at 10/min (`200×10` then `429×4`). Erase → 200, re-erase → 409, erased document → 404 on read, `objects_deleted: 1`. Archive is idempotent.
- **The team's own review discipline is a strength.** `review_notes.md` and `test_evidence.md` contain corrections of previously overstated results. That is rare and worth protecting.

### Main weaknesses

1. The chat stream **fails silently** when the inference service is down — HTTP 200, one status event, then nothing. The user gets a blank screen.
2. The **groundedness verdict is not a grounding signal** in the default configuration. It is decided by punctuation.
3. **Document versioning does not exist** in the product. Nothing ever writes `effective_to`.
4. **The frontend has no authentication**, and the impersonation control is enabled by default.
5. `GET /api/v1/collections` is **not ACL-filtered**, unlike every other read.
6. The documented command to load the eval corpus **crashes**.
7. **Streaming is not streaming** — the full answer is buffered before the first token is emitted.
8. Two of three personas (Steward, Platform Admin) have **no usable interface**.

### Business risks

- **Trust risk (highest).** The product's core promise is "cited, grounded, refuses to guess." A demo run without an API key will confidently label an unhelpful passage-dump as `grounded` and show the user a supporting-evidence banner. A prospect who notices this loses confidence in the differentiator the whole system is sold on.
- **Compliance risk.** The Auditability NFR ("every answer reconstructable: query, retrieved chunk IDs, model, prompt hash, cost") is satisfied in the *schema* and unreachable through the *API*. There is no `GET /queries/{id}`, no `GET /admin/erasures`. An auditor cannot be served without direct database access.
- **Regulatory risk.** Freshness is described as "a safety property, not a nicety" for the healthcare vertical. There is no way to produce a superseded version through the product, so no citation will ever carry the `superseded` badge.
- **Deployment risk.** No production auth path exists. Shipping requires `DEV_AUTH_BYPASS=true`, which trusts a plaintext header and lets any caller become any user in any tenant.

### Technical risks

- The identity engine and Redis client are module-level singletons bound to whichever event loop created them (documented as R-061, still open); the failure mode is silent — rate limiting fails open.
- `INGEST_SYNC=true` runs the whole parse→embed→index pipeline on a request thread. A 25 MB PDF will occupy that thread for the duration.
- Two divergent `problem+json` builders (`api/problem.py` and `api/services/problems.py`) already produce two different error envelopes on the same API.
- No caching layer despite Redis being present; every query re-embeds and re-retrieves.

### Missing functionality (Milestone A scope, by document)

`GET /api/v1/queries/{id}` · `GET /api/v1/admin/erasures` · `GET /api/v1/documents/{id}/versions` · `GET /api/v1/documents/{id}/versions/{vid}/content` · `PATCH /api/v1/documents/{id}` · `POST /api/v1/documents/{id}/reindex` · `GET /api/v1/ingestion-jobs` (+`/{id}`, `/{id}/retry`) · `PATCH`/`DELETE /api/v1/collections/{id}` · `GET`/`PUT /api/v1/collections/{id}/acl` · `GET`/`PUT /api/v1/documents/{id}/acl` · `GET /api/v1/tenants` · `GET /api/v1/users` · groups CRUD · `PUT /api/v1/users/{id}/roles` · `as_of` on search (R-030) · `messages` on chat.

All verified as 404 against the running API.

### Improvement opportunities

Ranked by value per unit of work: (1) make the abstention gate honest in fallback mode — a one-line guard, enormous credibility payoff; (2) define terminal SSE failure semantics; (3) ACL-filter collections — reuse `document_acl_predicate`'s resolution; (4) implement re-upload-as-new-version, which unlocks the entire freshness differentiator that is already modelled in the schema; (5) fix the corpus loader so quality numbers become reproducible.

#### IS-01 · Chat stream terminates silently when the inference service is unavailable

**Category:** Error handling / Reliability / UX · **Severity:** Critical · **Priority:** P0

**Description.** `POST /api/v1/chat/completions` commits `200 OK` and `Content-Type: text/event-stream` before retrieval runs. When `embed_query` raises `InferenceUnavailable`, Starlette cannot convert the handled domain error into a response — headers are already sent — so the stream just ends after the first `status` event. No `error` event, no `done` event, no terminal frame of any kind. The client cannot distinguish this from a successful empty answer.

**Steps to reproduce.**
1. Start Postgres, Redis, MinIO, and the API. Do **not** start the inference service.
2. `curl -i -N -X POST http://127.0.0.1:8000/api/v1/chat/completions -H 'X-Dev-User: acme-member' -H 'Content-Type: application/json' -d '{"question":"vacation days","stream":true}'`

**Expected.** Either a pre-stream `503 retrieval-unavailable` problem+json (as `POST /api/v1/search` correctly returns), or a terminal `event: error` frame followed by `event: done`.

**Actual.**
```
HTTP/1.1 200 OK
content-type: text/event-stream; charset=utf-8

event: status
data: {"stage": "retrieving"}

<stream ends>
```
Server log: `RuntimeError: Caught handled exception, but response already started.`

**User impact.** In the actual UI (`apps/web/src/app/(chat)/page.tsx`), `response.ok` is true, so the error branch never runs; the reader loop ends, `finally` sets `busy=false` and `status=null`, and `error` stays `null`. **The user sees the Ask button re-enable and nothing else appear.** No message, no retry cue. During any inference outage every user in every tenant experiences the product as broken-without-explanation. This also breaks the CI merge gate (documented as R-059/R-060, still open).

**Recommendation.** Resolve retrieval *before* returning `StreamingResponse` — run `retrieve()` in the route handler, let domain errors map to problem+json normally, and pass the hits into the generator. If that is undesirable, add `event: error` + `event: done` as a defined terminal pair in `run_chat`'s exception path and handle `error` in `handleEvent`. Cover with a test that runs chat with `INFERENCE_BASE_URL` pointed at a closed port.

#### IS-02 · Groundedness verdict is decided by punctuation, not by grounding

**Category:** Correctness / Trust / Product integrity · **Severity:** Critical · **Priority:** P0

**Description.** Without a live API key — the configuration `.env.example` ships and the README calls the default — the abstention gate is structurally inert:

- `api/services/chat.py:194` takes `extractive_fallback`, which concatenates the top 3 raw passages.
- `:201-224` manufactures synthetic citations, one per chunk, assigning `answer_sentence_idx = i` (0, 1, 2) **without reference to the answer's actual sentences**.
- `:228` sets `labels = ["entailed"] * len(citations)` — the entailment judge is skipped and its verdict assumed favourable.
- `citation_coverage` then measures those fabricated indices against sentences produced by splitting the concatenated passages on `[.!?]\s+`.

The verdict therefore depends on **how many sentence-ending periods happen to appear in the retrieved text**, and on nothing else.

**Steps to reproduce.** With no `ANTHROPIC_API_KEY`, ask three questions and read the `verdict` frame.

**Expected.** A fallback path that performs no synthesis and no entailment check must not claim the answer is grounded. `partial` at best; `unsupported` is the defensible default.

**Actual** (three consecutive live runs, same configuration):

| Question | Answer text | Verdict | Coverage |
| --- | --- | --- | --- |
| "How many vacation days do employees get?" | `Showing source passages — synthesis unavailable.` + 3 passages | **`grounded`** | 1.0 |
| "ACLSPLITTOKEN99" | same shape, 3 passages | `partial` | 0.6 |
| "What is the airspeed velocity of an unladen swallow?" | abstention message | `unsupported` | 0.5 |

The first row is the defect in one line: a passage dump that answers nothing was certified **grounded with 100% citation coverage**.

**User impact.** The UI renders a trust banner directly off this field — "Partially supported answer — check the cited sources" or the abstention notice. A `grounded` verdict shows *no* caveat at all, so the user is told, by silence, that a non-answer is fully supported. This is the exact failure mode ADR-011 was written to forbid ("a signal that nothing reads is not a control"), reintroduced one layer up: here the signal is read, but it is not measuring what its name says. For a system whose headline differentiator is unsupported-answer detection, this is the most damaging defect in the report.

**Recommendation.** Make degradation explicit rather than optimistic:
1. When `generation.stop_reason == "extractive_fallback"`, force `verdict = "partial"` (or `"unsupported"`) and skip coverage entirely — do not compute a number that cannot mean anything.
2. Never default entailment labels to `entailed`. `unrelated` is already the conservative default used in `judge_entailment`; use it here too.
3. Do not synthesise citations with sequential `answer_sentence_idx`. If citations were not produced by a citing model, emit them as *sources* without a sentence binding.
4. Add a unit test asserting that a fallback generation cannot yield `grounded`.

#### IS-04 · Document versioning and supersession are unimplemented in the product

**Category:** Feature completeness / Data model · **Severity:** High · **Priority:** P1

**Description.** The schema models versioning correctly — `document_versions.effective_to`, `uq_document_versions__one_current` (partial unique where `effective_to IS NULL`), `uq_document_versions__doc_sha`. The product never uses it. `apps/api/src/api/routers/documents.py:237-242` hardcodes `version_no=1, effective_to=None` on every upload, under a freshly minted `document_id`. A repo-wide grep finds exactly one writer of `effective_to`: `evals/harness/corpus.py:264` — the test-fixture loader.

**Steps to reproduce.**
1. Upload `qa.md` as `acme-steward` → `document_id: ef935ab2…`
2. Upload the identical bytes again → `document_id: 16c2ae9d…`, `version_id` new, `version_no` 1.
3. `SELECT count(*) FROM documents;` → both rows present, neither superseded.

**Expected.** Re-uploading a document produces `version_no = n+1`, sets `effective_to` on the prior version, and leaves old citations resolvable against the superseded version (KW-2).

**Actual.** Two unrelated documents. `content_sha256` is computed and a uniqueness index exists for it, but neither is ever consulted, because the scope is a `document_id` that is new every time.

**User impact.** Stewards cannot version anything — the corpus grows duplicates instead (the 45-document local corpus with repeated titles is this defect accumulating). The `superseded` staleness state that `_staleness_for_versions` computes and the UI renders as "Superseded by a newer version" is unreachable in production. Differentiator #3 and user story KW-2 are not delivered. For legal and healthcare verticals, where "which version governs" is the entire problem, this is the difference between a product and a demo.

**Recommendation.** Add `POST /api/v1/documents/{id}/versions` (or accept `document_id` on upload). In one transaction: set `effective_to = now()` on the current version, insert the new version at `version_no + 1`, enqueue ingest. Short-circuit on matching `content_sha256` with `409` or a no-op. Then implement `GET /documents/{id}/versions`.

#### IS-05 · `GET /api/v1/collections` is not ACL-filtered

**Category:** Authorization / Information disclosure · **Severity:** High · **Priority:** P1

**Description.** `apps/api/src/api/routers/collections.py:69-75` filters on `Collection.tenant_id` only. Every other read path (`list_documents`, `get_document`, `list_document_jobs`, both search arms) routes through `_readable_documents` / `document_acl_predicate`. Collections were missed.

**Steps to reproduce.**
```bash
curl -H 'X-Dev-User: acme-member' http://127.0.0.1:8000/api/v1/collections
curl -H 'X-Dev-User: acme-viewer' http://127.0.0.1:8000/api/v1/collections
```

**Expected.** Each caller sees only collections they hold a `read` grant on.

**Actual.** Both return the identical list, including `{"name":"Acme Legal","description":"Restricted legal material"}`. The same two users receive **demonstrably different** results from `GET /documents` and `POST /search`, confirming the inconsistency is specific to this endpoint.

**User impact.** Directly contradicts KS-5 ("I never see content from a document I am not authorized to read — *including in summaries or result counts*") and the README's claim that post-filtering "leaks result counts". Collection names and descriptions are themselves sensitive in the target verticals — "Project Harbour Diligence" or "2027 Restructuring" leaks the existence of the matter to anyone in the tenant. `GET /collections/{id}` has the same gap. It is also the source of the admin UI's collection dropdown, so stewards are offered upload targets they cannot write to.

**Recommendation.** Resolve the ACL once and filter: allow when `subjects.is_admin`, else `Collection.id.in_(resolution.allowed_collection_ids)`. Apply to both list and detail; return 404 (not 403) on detail, matching the document convention. Add a test asserting `acme-viewer` does not see `Acme Policies`.

#### IS-06 · `evals.harness.run --load-corpus` crashes

**Category:** Correctness / Reproducibility · **Severity:** High · **Priority:** P1

**Description.** `evals/harness/corpus.py:130-134` deletes stale chunks via ORM `session.delete(old)`. `Chunk.embeddings` is a `relationship` (models.py:327) with no `cascade="all, delete-orphan"`, so SQLAlchemy tries to null the child FK — which is `chunk_embeddings`' primary key. The worker does this correctly with a bulk `session.execute(delete(Chunk)...)` (`tasks/ingest.py:227`); the harness does not.

**Steps to reproduce.** Load the corpus once (or run any ingest), then run the README's documented command:
`uv run python -m evals.harness.run --load-corpus`

**Expected.** Fixtures are re-ingested idempotently and scoring proceeds.

**Actual.**
```
AssertionError: Dependency rule on column 'chunks.id' tried to blank-out
primary key column 'chunk_embeddings.chunk_id' on instance '<ChunkEmbedding …>'
```

**User impact.** The only documented path to a clean, reproducible quality measurement is broken on the second run. Every published retrieval number is therefore measured against whatever residue is in the developer's database — which is precisely the R-046 problem the team already identified, now with no working way out of it. It also blocks R-031 (wiring eval into CI).

**Recommendation.** Replace the ORM loop with `await session.execute(delete(Chunk).where(Chunk.document_version_id == version.id))`, matching the worker, and let the DB-level `ondelete="CASCADE"` do the work. Add `passive_deletes=True` to the relationship so the ORM never attempts the null-out.

#### IS-08 · The web application has no authentication, and impersonation is on by default

**Category:** Security / Feature completeness · **Severity:** High · **Priority:** P1

**Description.** `apps/web/src/lib/api.ts` is the entire auth layer:
```ts
export const DEV_AUTH = (process.env.NEXT_PUBLIC_DEV_AUTH ?? "true").toLowerCase() === "true";
export function authHeaders(user: string) { return DEV_AUTH ? { "X-Dev-User": user } : {}; }
```
There is no sign-in route, no OIDC redirect, no token acquisition, storage, refresh, or logout. Two failure modes follow:

- With `NEXT_PUBLIC_DEV_AUTH=false` (correct for production) the app sends **no credentials at all** and every request 401s. The UI is non-functional.
- The default is **`true`**. A build that forgets the variable ships the impersonation dropdown — pick any of four users — to end users.

**Expected.** An OIDC code flow against the Keycloak realm already in compose, with tokens on the API calls, a session, and a logout control. Dev impersonation opt-**in**, not opt-out.

**Actual.** The app functions only against `DEV_AUTH_BYPASS=true`, which the README itself describes as "any caller can become any user, in any tenant."

**User impact.** Sign Up → Login → Dashboard → Logout, one of the flows named in the brief, cannot be tested because none of it exists. There is no deployable configuration: one setting makes the UI dead, the other makes the API open. Note this is stated plainly in `current_task.md` item 8 — the gating for `NEXT_PUBLIC_DEV_AUTH` is correctly called "a guard, not a solution."

**Recommendation.** Flip the default to `false` today (one line, removes the insecure default immediately). Then implement the OIDC flow — the realm, issuer, audience and JWKS URL are already configured and `_verify_oidc_token` already validates properly.

#### IS-09 · "Streaming" buffers the entire answer before emitting the first token

**Category:** Performance / UX / Requirements conflict · **Severity:** High · **Priority:** P1

**Description.** `api/services/chat.py:153-190` consumes the model stream into `answer_parts` **without forwarding**, because the groundedness verdict is only computable once the whole answer exists. The answer is then re-sliced into 96-character frames at `:256`. Time-to-first-token equals full generation latency plus the judge call.

The reasoning is sound and the code comment defends it well — forwarding tokens and retracting them afterwards would defeat the abstention gate entirely. The defect is that **the product requirements were never reconciled with the decision**:

- KS-6: "The answer starts streaming quickly rather than appearing all at once after a long wait."
- §7.4: "Time to first token (p95) ≤ 2.5 s (`dev-cpu`) / ≤ 1.2 s (`cloud-gpu`)".

Both are unachievable by construction with `claude-opus-5` at `effort: high` and `max_tokens: 64000`.

**User impact.** Users wait for the complete generation staring at "Status: generating", then receive the whole answer in a burst. On a long answer that is tens of seconds of apparently-frozen UI. The SSE transport, the parser, and the token frames all exist but deliver no perceived-latency benefit.

**Recommendation.** Pick one and write it down. Either (a) accept buffering, delete the TTFT targets and reword KS-6 to an end-to-end target, and replace the raw `Status: generating` with a real progress affordance; or (b) stream tokens optimistically into a visually-provisional region that is replaced or retracted on an `unsupported` verdict. Also fix the 96-char slicing, which splits mid-word (`onl` / `y secret handbook`, `[V` / `acation Policy`) — slice on whitespace boundaries.

#### IS-10 · Citation numbering is wrong and produces unreachable source cards

**Category:** UI / Correctness / Accessibility · **Severity:** High · **Priority:** P1

**Description.** In `(chat)/page.tsx` the superscript marker is the **sentence** index (`[{index + 1}]`, line 301) and the source card reuses it (`[{c.answerSentenceIdx + 1}]`, line 348). Three consequences:

1. Numbering is non-sequential and misleading. A citation on sentence 5 renders `[6]` even when it is the second source shown.
2. When `answerSentenceIdx ≥ sentences.length`, the source card renders with `id="citation-N"` but **no anchor in the text points to it** — an orphan.
3. When two citations share a sentence, two `<li>` elements get the **same `id`** — invalid HTML; the anchor reaches only the first.

**Steps to reproduce.** Ask "How many vacation days do employees get?" in the shipped no-key configuration. The server emits citations with `answer_sentence_idx` 0, 1, 2. The answer text (`Showing source passages — synthesis unavailable.\n\n[Eng Handbook]\n…`) contains exactly one `[.!?]\s+` boundary → 2 sentences.

**Expected.** Every source card is reachable from the answer; markers are sequential; ids unique.

**Actual.** Citation 2 renders a source card at `#citation-2` with no `[3]` link anywhere. Citations 0 and 1 attach sources to the framing sentence "Showing source passages — synthesis unavailable.", which asserts nothing.

**User impact.** Citations are the product's central trust affordance. A user clicking through evidence finds sources that link nowhere and numbers that do not correspond to the list order. Keyboard and screen-reader users are worse off — the `aria-label` promises "Jump to source for sentence N" and the anchor target may not exist. Root cause is shared with IS-02: the fallback path fabricates sentence indices.

**Recommendation.** Decouple display numbering from sentence index: number sources 1..n in emission order, key each card by `chunkId+start+end`, and have each in-text marker link to its own source's unique id. Clamp or drop citations whose sentence index exceeds the rendered sentence count. Note the client's `splitSentences` and the server's `split_sentences` differ on leading whitespace — unify them or send offsets rather than indices.

**Category:** Validation / Data quality · **Severity:** Medium · **Priority:** P2

## 5. Release Recommendation

## **No.**

Not ready for production.

### Technical justification

Three of the blocking reasons are independent of scope, effort, or timeline, and none is a matter of polish.

**1. There is no production deployment configuration.** The frontend has no authentication (IS-08). With `NEXT_PUBLIC_DEV_AUTH=false` it sends no credentials and 401s on every request; with `true` it ships a user-impersonation dropdown and requires the API to run `DEV_AUTH_BYPASS=true`, which the repository's own README describes as letting "any caller become any user, in any tenant." There is no third setting. A system cannot be released when no configuration of it is both functional and safe.

**2. The product's defining safety property does not hold as shipped.** Unsupported-answer detection is Differentiator #6 and the source of the "refuses to guess" claim. In the configuration this repository ships — no `ANTHROPIC_API_KEY`, the documented default — the verdict is computed from fabricated citation indices and hardcoded `entailed` labels, so it reduces to a count of sentence-ending periods in the retrieved passages (IS-02). It was observed certifying the text *"Showing source passages — synthesis unavailable"* as **`grounded` with 100% citation coverage**. A user is shown a trust signal that is measuring nothing. In the target verticals — finance, legal, healthcare — a false assurance of groundedness is worse than no assurance, because it is actionable.

**3. The system fails silently.** When inference is unavailable, chat returns `200 OK`, emits one status event, and stops (IS-01). No error frame, no terminal frame, no client-observable difference from success. The UI returns to idle showing nothing. Silent failure in the primary user flow is disqualifying on its own; combined with a readiness probe that reports `ready` throughout (IS-13), an outage is invisible to users, to operators, and to the load balancer simultaneously.

Beyond those: the merge gate is red (IS-03); the documented eval-corpus command crashes, so no quality claim is reproducible (IS-06); measured retrieval is 0.364 against a 0.90 target with cross-lingual at 0.000 against 0.85 (IS-07); document versioning — the basis of the freshness differentiator, the versioning ADR, and user story KW-2 — has no code path in the product (IS-04); and the audit trail the compliance story rests on is written but unreadable (IS-14).

### What this is, accurately

A very good architectural foundation with a demonstrably incomplete product on top of it. The tenant isolation, ACL pre-filtering, RLS enforcement, transactional ingest discipline, and documentation are genuinely above the standard for an MVP, and several of the hardest problems — compiling ACLs into the ranking query, keeping tenant context transaction-local across a mid-request commit, refusing to disambiguate a subject that exists in two tenants — are solved correctly and for the stated reasons. The team's own `review_notes.md` and `current_task.md` already identify roughly half of what this review found, with the right priorities. That is a healthy project, not a troubled one.

It is not, today, a releasable one.

### Path to "Yes, with reservations"

A defensible internal-demo or design-partner release needs, in order:

1. **IS-02** — force a non-`grounded` verdict on the fallback path; never default entailment to `entailed`. Small change, largest credibility return in the report.
2. **IS-01** — define terminal SSE failure semantics; handle `error` in the client.
3. **IS-08** — flip `NEXT_PUBLIC_DEV_AUTH` to default `false` immediately; implement the OIDC flow against the Keycloak realm that is already configured.
4. **IS-05** — ACL-filter collections.
5. **IS-06 → IS-07** — fix the loader, load a clean corpus, re-measure, publish the numbers with their profile.
6. **IS-03** — green the merge gate.
7. **IS-04** — implement re-upload-as-new-version. This single change unlocks the freshness differentiator that is already fully modelled in the schema.

Items 1–4 are days of work, not weeks, and they convert the two most damaging defects in this report into non-issues. Items 5–7 are what separate a demo from a product.
