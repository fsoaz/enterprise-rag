## 1. Executive Summary

**Verdict:** Do Not Release
**Risk Level:** High
**Effort Estimate:** Moderate rework — no architectural rebuild needed. The defects concentrate in configuration wiring, one classifier threshold, and one verdict branch.

### Top 3 Risks

1. **The system cannot be set up from a clean clone** (BUG-001, BUG-002, BUG-006). The web app's env template is gitignored, Compose reads `.env.example` instead of the `.env` the README tells you to create, and the entire `docs/` tree the README cites as evidence is untracked. A reviewer following README §Setup gets a stack that silently stays in degraded mode.
2. **The headline abstention gate has a dead input** (BUG-004). `unrelated` — documented as the conservative fallback label when the entailment judge cannot match a claim — is never read by `groundedness_verdict`. Verified: all-`unrelated` labels return `grounded`, byte-identical to all-`entailed`. Two of the three declared gate inputs are load-bearing; the third is decorative.
3. **Legitimate corporate policy text is silently unretrievable** (BUG-003). The injection scorer hard-blocks any chunk scoring ≥ 0.8, and realistic sentences such as *"Employees must not jailbreak or root company-issued mobile devices"* score 0.95. Ingest reports success; the content simply never comes back. The product's core promise — answers grounded in your own policies — fails precisely on security policies.

### BUG-001 — `apps/web/.env.example` is gitignored, so setup step 2 fails from a clean clone

- **Domain:** A. Functional & Flow Integrity
- **Severity:** Critical · **Priority:** P0

**Steps to Reproduce**

1. `git clone` the repository into an empty directory.
2. Follow README line 97: `cp apps/web/.env.example apps/web/.env.local`

**Expected Result:** The template copies; the web app gets `NEXT_PUBLIC_DEV_AUTH` and `NEXT_PUBLIC_API_BASE`.

**Actual Result:** `cp: cannot stat 'apps/web/.env.example': No such file or directory`. The file exists in the working tree but is untracked.

**Recommendation:** Narrow the ignore rule so example templates are exempt, then commit the template. Add a clean-clone setup check to CI so this class of defect cannot recur.

**Suggested Fix Location:** `apps/web/.gitignore:34`

### BUG-002 — Compose loads `.env.example`, so the `.env` the README tells you to create is ignored

- **Domain:** A. Functional & Flow Integrity
- **Severity:** High · **Priority:** P0

**Steps to Reproduce**

1. `cp .env.example .env` (README line 96).
2. Edit `.env` and set a real `ANTHROPIC_API_KEY=sk-ant-...`.
3. `make up`.
4. Ask any question in the UI.

**Expected Result:** Synthesized, cited answers from the live model.

**Actual Result:** The `api` container receives `ANTHROPIC_API_KEY=sk-ant-replace-me` from the example file. `_use_live_llm()` rejects the `replace-me` suffix, so the system runs the extractive/degraded path and abstains — indistinguishable from a corpus that genuinely has no answer.

**Evidence**

- `infra/compose/docker-compose.yml:86-87` and `:116-117` — `env_file: ../../.env.example` for both `api` and `worker`.
- `.env.example:42` — `ANTHROPIC_API_KEY=sk-ant-replace-me`.
- `apps/api/src/api/services/chat.py:99` — `_use_live_llm` rejects keys ending in `replace-me`.
- The same mechanism defeats README line 119 ("set `DEV_AUTH_BYPASS=true` in `.env`"), since `api` reads `DEV_AUTH_BYPASS: ${DEV_AUTH_BYPASS:-false}` from Compose's own interpolation scope, not the repo-root `.env`.

**User Impact:** The documented path to enabling the product's primary feature has no effect, and the failure presents as correct abstention behaviour rather than as a misconfiguration. This is the most likely reason a reviewer concludes the system "doesn't answer anything."

**Recommendation:** Point `env_file` at `.env` and treat `.env.example` strictly as a template. Have the API log a single explicit warning at startup when it starts in degraded mode, naming the reason.

**Suggested Fix Location:** `infra/compose/docker-compose.yml:86,116`; `apps/api/src/api/main.py` (startup diagnostic)

### BUG-003 — Injection scorer hard-blocks legitimate policy content from both retrieval arms

- **Domain:** A. Functional & Flow Integrity / F. Security Surface
- **Severity:** High · **Priority:** P1

**Steps to Reproduce**

1. Upload a security policy containing *"Employees must not jailbreak or root company-issued mobile devices."*
2. Wait for ingest to report `succeeded`.
3. Ask "Can I jailbreak my work phone?"

**Expected Result:** A grounded answer citing that clause.

**Actual Result:** The chunk is excluded from both retrieval arms and the system abstains. No error, no warning, no indication in the admin UI that any content was withheld.

**Evidence** — executed against the real scorer:

```
0.95  Employees must not jailbreak or root company-issued mobile devices.
0.95  Section 4.2: Jailbreaking of corporate devices is prohibited.
0.95  This guideline covers prompt injection risks when using AI assistants.
0.90  Staff should disregard previous versions of this policy after 1 Jan.
0.90  Ignore all prior guidance on expense limits; the new table applies.
0.60  You are now required to complete annual security training.
0.50  Managers must always respond to escalations within 24 hours.
```

- `packages/domain/src/domain/types.py:89` — `INJECTION_RISK_BLOCK = 0.8`.
- `packages/retrieval/src/retrieval/dense.py:66` and `lexical.py:314` — both filter `Chunk.injection_risk < INJECTION_RISK_BLOCK`.
- `apps/worker/src/worker/pipeline/chunk.py:63-64` — bare substring tests for `"jailbreak"` and `"prompt injection"` assign 0.95 with no surrounding context.

**User Impact:** Security and AI-usage policies — the documents most likely to contain these words — become the documents the system cannot answer about. The existing `test_injection_risk_does_not_block_policy_language` benign set (`apps/worker/tests/test_chunk.py:69`) does not include any of the five sentences above.

**Recommendation:** Two separable changes. First, require the vocabulary terms to co-occur with an imperative aimed at the assistant rather than matching as bare substrings. Second, make blocking observable: surface withheld-chunk counts on the ingestion job so a curator can see that content was excluded and why.

**Suggested Fix Location:** `apps/worker/src/worker/pipeline/chunk.py:42-107`; `apps/worker/tests/test_chunk.py:69`

### BUG-004 — `unrelated` entailment labels do not affect the groundedness verdict

- **Domain:** A. Functional & Flow Integrity
- **Severity:** High · **Priority:** P1

**Steps to Reproduce:** Call `groundedness_verdict` with labels that are entirely `unrelated` and otherwise-passing inputs.

**Expected Result:** Per `packages/llm/src/llm/client.py:429` — *"Unmatched pairs stay `unrelated` — the conservative label"* — a wholly unrelated set should not certify an answer as grounded.

**Actual Result:** Identical outcome to fully entailed labels.

**Evidence** — executed:

```
all unrelated, high coverage/conf -> grounded
all entailed                      -> grounded
one contradicted                  -> unsupported
```

- `packages/llm/src/llm/groundedness.py:122-128` branches only on `"contradicted"` and `"partial"`. The string `"unrelated"` does not appear anywhere in that module.
- The one test that uses the label (`packages/llm/tests/test_groundedness.py:19-25`) also passes `coverage=0.2, confidence=0.01`, so it returns `unsupported` for unrelated reasons and cannot detect this.

**User Impact:** When the judge's echoed indices fail to match — the exact failure R-044 was written to make safe — the conservative default silently degrades to a no-op, and the answer ships as `grounded`. The entailment judge is billed for on every live query (`apps/api/src/api/services/chat.py:416-431`) while contributing nothing except in the `contradicted` and `partial` cases.

**Recommendation:** Decide and encode what a majority-`unrelated` label set means for the verdict, then pin it with a test that varies only the labels.

**Suggested Fix Location:** `packages/llm/src/llm/groundedness.py:110-128`; `packages/llm/tests/test_groundedness.py:19`

### BUG-005 — Erasure leaves the erased document's text in `queries.answer_text`

- **Domain:** F. Security Surface
- **Severity:** High · **Priority:** P1

**Steps to Reproduce**

1. With no live API key (degraded path), ask a question answered by document D.
2. Note the returned `query_id`.
3. `POST /api/v1/admin/documents/{D}/erase` as an admin.
4. `GET /api/v1/queries/{query_id}` as the user who asked.

**Expected Result:** Per `apps/api/src/api/routers/admin.py:113-119` — *"erased text must not survive in a stored answer"* — no erased content is returned.

**Actual Result:** ***Potential Concern (static).*** `answer_text` is retained and, on the degraded path, contains the chunk bodies verbatim. The erase handler deletes `Chunk` rows (cascading to `chunk_embeddings` and `query_citations`) and sets `erased_at`, but never touches the `queries` table.

**Evidence**

- `packages/llm/src/llm/client.py:463-464` — `parts = [f"[{c.document_title}]\n{c.body}" ...]`; the full chunk body becomes the answer text.
- `apps/api/src/api/services/chat.py:376` — persists `answer_text=answer_text`.
- `apps/api/src/api/routers/admin.py:137-172` — no `Query` mutation anywhere in the erase path.
- `Query` has no FK to `chunks` or `document_versions`, so no cascade reaches it.
- There is no retention sweep: `apps/worker/src/worker/tasks/` contains only `ingest.py` and `noop.py`.

**User Impact:** Right-to-erasure is incomplete in exactly the case the code comments claim to cover, and the audit record in `erasure_log` asserts a completeness that was not achieved. `retrieved_chunk_ids` is also left pointing at deleted rows.

**Recommendation:** Bring `queries` into the erasure transaction — null or redact `answer_text` and `retrieved_chunk_ids` for queries that cited an erased version — and record the count in `erasure_log` alongside `citations_affected`.

**Suggested Fix Location:** `apps/api/src/api/routers/admin.py:137-172`; `packages/db/src/db/models.py:436` (`Query`)

### BUG-008 — Two disagreeing server-side language detectors; Portuguese questions get parsed with the English dictionary

- **Domain:** A. Functional & Flow Integrity
- **Severity:** Medium · **Priority:** P1

**Steps to Reproduce:** Ask, in Portuguese: *"Quanto tempo guardamos os registros?"*

**Expected Result:** Both the FTS config and the localized system message resolve to `pt`.

**Actual Result:** They disagree. `domain.text.detect_supported_language` returns `pt` (matches the `os` marker). `retrieval.pipeline._detect_language_hint` returns `en`, because its 9-entry marker set — `{de, que, não, nao, para, uma, política, politica, segurança}` — contains none of the question's tokens.

**Evidence**

- `packages/retrieval/src/retrieval/pipeline.py:49-53` vs `packages/domain/src/domain/text.py:97-109`.
- The consequence is specifically what `packages/retrieval/src/retrieval/lexical.py:222-230` documents as the failure to avoid: with `config="english"`, Portuguese stop words survive `to_tsvector` as content lexemes, so `_matched_term_count` counts `os`, `o`, `de` toward the `LEXICAL_MIN_EVIDENCE_TERMS = 2` degraded-mode evidence threshold.
- A third detector exists in the frontend (`apps/web/src/app/(chat)/page.tsx:129`) with yet another rule set, used to set the `lang` attribute a screen reader reads.

**User Impact:** Portuguese queries get worse ranking and can clear the degraded-mode evidence bar on stop words alone — a self-certifying result the code was explicitly restructured to prevent.

**Recommendation:** Collapse to one detector. `domain.text` already lives in the shared package precisely so both callers can use it; `_detect_language_hint` exists only to avoid an import that is already allowed.

**Suggested Fix Location:** `packages/retrieval/src/retrieval/pipeline.py:49-53`

### BUG-009 — Real BGE-M3 vectors are written under the version label `stub-v0`

- **Domain:** A. Functional & Flow Integrity
- **Severity:** Medium · **Priority:** P2

**Steps to Reproduce**

1. Ingest a corpus with `INFERENCE_BACKEND=stub` (the CI configuration).
2. Restart with `INFERENCE_BACKEND=bge` (the shipped default).
3. Query.

**Expected Result:** Either the stale stub vectors are recognised as belonging to a different model and ignored, or a re-embed is required.

**Actual Result:** ***Potential Concern (static).*** Both backends write and read `model_version="stub-v0"`, so the primary key `(chunk_id, model_name, model_version)` treats them as the same vector space. Dense search silently ranks real BGE-M3 query vectors against hash-derived stub passage vectors.

**Evidence**

- `.env.example:36` — `INFERENCE_BACKEND=bge` — alongside `.env.example:60` — `EMBEDDING_MODEL_VERSION=stub-v0`.
- The same default is hardcoded at `packages/retrieval/src/retrieval/dense.py:30` and `apps/worker/src/worker/pipeline/embed.py:55`.
- `.github/workflows/ci.yml:185` runs `INFERENCE_BACKEND: stub`.
- `packages/db/src/db/models.py:361` defines the composite primary key.

**User Impact:** Retrieval quality collapses with no error surface — every query returns confidently-ranked nonsense. Symmetrically, a genuine model/version mismatch produces zero dense hits and an unexplained abstention, because `dense_search` filters on equality with no fallback and no log.

**Recommendation:** Derive `EMBEDDING_MODEL_VERSION` from the backend actually loaded rather than from an independent variable, and log a warning when a dense query matches zero embedding rows for the active version.

**Suggested Fix Location:** `packages/retrieval/src/retrieval/dense.py:27-31`; `apps/worker/src/worker/pipeline/embed.py:54-55`; `.env.example:60`

- **Domain:** D. Interaction & Accessibility

**Steps to Reproduce**

**Suggested Fix Location:** `apps/web/src/app/(chat)/page.tsx:92-97,328-330`

### BUG-011 — OIDC provider `error_description` is reflected verbatim onto the sign-in screen

- **Domain:** F. Security Surface
- **Severity:** Medium · **Priority:** P2

**Steps to Reproduce:** Navigate a victim to `/api/auth/callback?error=x&error_description=<attacker text>`.

**Expected Result:** A fixed, application-authored error message.

**Actual Result:** The value is copied into the `auth_error` query parameter and rendered in the sign-in alert region.

**Evidence**

## 5. Missing MVP Features

Capabilities a reasonable user of this product would expect and cannot reach:

1. **Query history.** `GET /api/v1/queries/{id}` exists and enforces ownership, but no UI lists past questions. A user who refreshes loses every answer they have received.
2. **Source document preview or download.** Citations show a snippet and a character range but nothing opens the underlying document. `docs/standards/api_rules.md §13` (per R-003) describes a proxied download path; no route implements it and no UI links to one.
3. **ACL administration.** `POST /api/v1/acl/entries` is admin-only and has no interface. Granting a colleague access to a collection requires hand-crafting an HTTP request — for the feature the README leads with.
4. **Erasure interface.** `POST /admin/documents/{id}/erase` and `GET /admin/erasures` are API-only. A compliance action with an audit log has no operator surface.
5. **Search UI.** `POST /api/v1/search` supports four strategies and `top_k`; nothing in the frontend calls it. The retrieval-strategy comparison named as a differentiator is unreachable outside the eval harness.
6. **Version history UI.** `GET /documents/{id}/versions` exists; the admin page never calls it. Document versioning underpins the freshness badges users see, with no way to inspect the chain.
7. **Language switcher before sign-in.** `LocaleSwitch` renders only inside the authenticated shell (`apps/web/src/components/auth-gate.tsx:85`) or under `DEV_AUTH`. The sign-in screen localizes from the cookie or `Accept-Language` with no way to change it — and the cookie cannot exist yet on a first visit.
8. **Reindex.** The README architecture diagram lists the Celery worker as handling "ingest · reindex · freshness". Only `ingest` exists; `apps/worker/src/worker/tasks/` holds `ingest.py` and `noop.py`. There is no way to re-embed a corpus after a model change — which BUG-009 makes necessary.

## 6. Positive Findings

1. **The token really never reaches the browser.** The BFF is properly built, not merely claimed: `HttpOnly` / `SameSite=Lax` cookies, `timingSafeEqual` on the OAuth state, PKCE S256, an issuer-origin check before rewriting discovery endpoints to an internal host, hop-by-hop header stripping, `encodeURIComponent` on every proxied path segment, a same-origin gate on mutations, and — a genuinely thoughtful detail — the request body buffered to an `ArrayBuffer` so a near-expiry POST can be retried after a token refresh instead of failing on a locked stream.

2. **The abstention gate is structured so streaming cannot defeat it.** `run_chat` consumes the model stream without forwarding, computes the verdict, and emits from a single point (`apps/api/src/api/services/chat.py:341-344`). This is the correct fix for R-017 rather than a patch over it, and the `verifying` status stage keeps the buffering period legible to the user instead of appearing frozen.

3. **The integration-test database guard fails closed by design.** `tests/integration_database.py` refuses to infer its target from `DATABASE_URL` and rejects any database whose name is not visibly test-designated. That is a rare piece of discipline, and it is the reason BUG-007's noisy failure is safe rather than destructive.

4. **Upload validation trusts content, not the client.** `_detect_media_type` ignores `Content-Type` entirely and sniffs magic bytes and control-character ratios, `_read_capped` aborts mid-stream at the size limit rather than buffering first, and NUL bytes are stripped at decode. The comments explain *why* at each site, which is what made this review fast.

multi-sentence chunk fixture. A suite that only ever gains the exact strings a reviewer published cannot
detect the next variant.

### R4-1 — BUG-005: erasure now redacts stored answers

The redaction runs **before** `delete(Chunk)`, which is the ordering the fix depends on: `query_citations`
cascade-deletes off `chunks.id`, so computing `cited_query_ids` after the delete would return an empty
set. Verified in source order at `apps/api/src/api/routers/admin.py:154-193`.

Two independent paths catch an affected query, which is the right belt-and-braces for this:

1. `cited_query_ids` — queries with a `query_citations` row pointing at an erased version.
2. `overlap_query_ids` — queries whose `retrieved_chunk_ids` intersects the erased chunk set. This
   catches the abstention case, where the answer was built from retrieved chunks but no citation row was
   ever written.

The array predicate compiles to a real Postgres `&&` on a typed array, not a Python-side filter:

```sql
SELECT queries.id FROM queries
WHERE queries.tenant_id = %(tenant_id_1)s::UUID
  AND queries.retrieved_chunk_ids && %(retrieved_chunk_ids_1)s::UUID[]
```

`Query.answer_text` and `Query.retrieved_chunk_ids` are both `nullable=True`
(`packages/db/src/db/models.py:455-458`), so the `UPDATE … SET NULL` cannot fail a NOT NULL constraint.
`queries_affected` is recorded on the audit row. `Query.question` is deliberately retained — it is the
user's own input, not the erased document's text, and erasing it would destroy the audit trail the
erasure log exists to provide.
